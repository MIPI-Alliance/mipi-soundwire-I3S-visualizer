# SWI3S Studio v3.0.17

Adds support for Saleae `.sal` internal blob version 4, and corrects the large-capture memory
guard together with three per-interaction performance defects.

Per-release detail is the changelog block at the top of `swi3s_studio/__init__.py`, newest
first; this file is the summary of the 3.0.17 entry. Gated on every supported platform before
tagging.

## Ingest

- Logic 2 `.sal` digital blobs at version 4 now open. The format is identical to version 3 —
  only the version field changed — so they decode through the same reader. Verified against a
  v0 export of the same capture (delta arrays equal, samples equal after the constant frame
  offset the metadata header carries) rather than accepted because the parse looked plausible.
- Accepted blob versions are 0, 3 and 4, pinned by a test. Any other version is refused with a
  clear error rather than decoded on the assumption that the format is unchanged: refusing a
  readable file is an inconvenience, while decoding a changed format yields a plausible wrong
  bus.

## Large captures

- The predicted peak memory of an open now applies the decode transient to the edge-array
  term. The whole-file path previously omitted it and under-predicted the real peak by up to
  3.6x.
- The memory budget is the lower of a fraction of free memory and an absolute ceiling, so a
  machine with more RAM no longer opens more without asking. The failure previously grew with
  the hardware.
- **Analyzer > Open Capture Time Window...** opens a chosen start and length of a `.sal` at any
  size. Previously a time window was only offered when the size guard forced one.
- A windowed open now costs the window rather than its start offset: a 0.5 s window near the
  end of a long capture went from 28 s to 1.9 s.

## Performance

- The Decoded Samples pane holds a smaller window, so a cursor move that leaves the loaded
  range rebuilds far fewer table items (48,000 before). A move inside the range rebuilds none.
- TX-map persistence scans above a size threshold now run on a worker thread instead of the
  GUI thread. The threshold was set 16x above the budget its own documentation stated, which
  froze the GUI for ~550 ms per move on short captures rather than long ones.
- Extending the Decoded Samples window no longer triggers a second load at the opposite end.

## Tests

- Per-cursor-move cost is asserted as deterministic counts — rows built, which thread a region
  scan runs on, hidden panes doing no work — alongside wall-clock ceilings, since a ceiling on
  a function cannot express which thread it ran on, which is how the worst of these shipped
  green.
- The memory prediction is checked against a measured load rather than trusted.
- Version 4 coverage is parametrised over both versions and asserts they decode identically, so
  a reader that special-cased v4 would not pass.

## Not in this release

The per-platform standard-library route for reading free memory, and the tiered fallback for
when it cannot be read at all. Both landed after this tag and ship in 3.0.18. An earlier
hand-written version of these notes listed them as 3.0.17 work; this file exists so that a
release description cannot claim work the tag does not contain.

## Differences from the release tag

The published tree is not byte-identical to `v3.0.17`, and two of the reasons are not
derivable from the tool that assembles it, so they are recorded here.

- **Nine files of prose.** Eight — comments, docstrings and documentation, no product code —
  described the development environment rather than the software: a finding attributed to
  whoever noticed it, a named test platform, a capture or a machine identified by label rather
  than by measurement. All are generalised. Every measurement is unchanged, the changelog
  carries exactly the 17 entries the tag carries, and `__version__` is 3.0.17. The decode core,
  the reference model, the UI and every assertion are byte-identical.
- **This file.** It postdates the tag, because the one-description-per-release rule it
  implements came out of how this release was described. A tree built from the tag alone would
  not contain it.

The publish branch was rebuilt once, on 2026-08-21. Its first tip generalised three docstrings
and one changelog line and was edited after assembly, so it could not be reproduced from any
commit; the current one is assembled by `tools/publish_tree.py` from a single recorded source
commit. The two trees differ only in comments, docstrings and documentation.
